# Web bakeoff versus native — look parity audit

## Conclusion and evidence limits

**A3's web grades are not currently a reliable proxy for native grades.** The bakeoff replaces several shared material/data consumers, uses different lighting/exposure and water composition, rebuilds foliage, and lacks exported context. A web improvement remains a web result until the native equivalent is tested; neither platform is an accepted finished target. Do not port native's visible defects merely to force parity.

Read-only audit at main `b474bf5`; no code, new capture, export or score. Frame evidence comes from [A3's exploratory comparison](../review/native-vs-web-matched-comparison.md) (native `e5a0a3e`; web `1580115`, delivery `c8c361d`) and [A2 palette diagnosis](palette-diagnosis.md), filed `0d6a222`. Source findings below describe the inspected paths; a current code path is not proof it generated every historical frame. The frame observations are **A3's filed observations**, not a new visual grading session.

A3 reports native preference for materials, ground, foliage and light at40/150 m; saturation ties at both heights. At600 m native is preferred descriptively in all five aspects. All six images still scored **2/5 overall and every visible aspect**; sky N/A. Six presentations are not six independent reviewers. No fully matched preference was awarded: native resolved eye is0.16 m higher; native exposure gain is unrecorded; native wind0 versus web10 km/h; web fixed authored lighting differs from native resolved sun; native600 repeat brightness remains unstable; context content differs. Do not attribute the visual preferences to one shader term, calculate a cross-platform EV delta, or claim a causal score gain.

## Inventory and correction ownership

Scope is the static map scene and listed ground/light/water/vegetation differences, plus weather/LOD/grade paths that confound them. It is not a complete audit of characters, host UI, animation or every weather state. `Shared/exported` means attributes or geometry exist in the export path, **not** that the bakeoff consumes them correctly or that every old package has the current schema. `Renderer` means shader/material/runtime work: parity needs aligned platform implementations, but where native already implements the intended rule, only the web consumer may need editing. “Two changes” must not be read as permission to alter a working native path unnecessarily.

Cost notation: **0/0** = expected incremental main triangles/draws for an in-place shader/material correction, not measured performance. Shader time is **unmeasured for every proposed fix**. Existing hardware timing cannot attribute the cost of these differences. Shadow geometry/caster work is separate; no new shadow passes assumed unless explicitly stated.

## What is actually shared, and how to avoid duplicate fixes

`WorldPackage.swift` serializes mesh extras and paint, and the base web material can consume several native-like attributes. The **effective bakeoff path is a replacement**, so base viewer support must not be reported as bakeoff support. For lot mixing, joints and baked AO, validate actual attribute flags/values in the pinned package, then repair the web consumer first. A shared generator palette edit would also affect native and still be overwritten by bakeoff. For wall colour, choose one authoritative resolution location before changing either side; preserve explicit mapped colour precedence and uncertainty.

Context requires new shared delivery plus web consumption; it is not an ambient-light problem. Vegetation is not a bit-identical shared mesh: reconcile recipe/attribute semantics before claiming a shader-only port. Renderer-specific lighting, tone mapping, water and shadow behavior require independent native/web implementation checks even when both use the same JSON. Shared inputs make parity possible, not automatic. Implementation ownership remains P2 generator/attributes, A4 package/loader handoff, A2 bakeoff, 5A native/light review, A3 scoring.

## When web scores can be trusted as evidence for native

Until these conditions hold, keep **separate platform scoreboards**. Web is useful for testing its own changes and for spotting obvious shared geometry/data mistakes, not predicting native look grades.

1. Pin exported dataset/generator/registry versions, loaded coverage and actual camera/projection matrices; resolve0.16 m offset, near/far, FOV, aspect and drawable differences without image warping.
2. Resolve a common sun/weather/phenology/atmosphere state, log actual exposure and freeze/replay animation; fix native600 repeat noise before matched comparisons. Same UTC is not equivalent illumination.
3. Remove or explicitly label the lawn, pavement and family-wall overrides; verify consumed fields rather than assuming JSON equality. Use one colour transfer per renderer, no unproven double-conversion diagnosis.
4. Match or explicitly isolate foliage mesh/LOD and shadow-caster coverage. Do not grade a geometry replacement as a lighting comparison. Context must be equivalent or excluded from a narrowly scoped crop declared before review; full600 m grades still require full-world coverage.
5. Score new matched pairs only in a separately authorized task, randomized and with repeat controls, on each platform against approved calibration. Retain per-platform costs: shader-only estimates0/0 do not prove frame-time parity. No score promotion inferred by this audit.
