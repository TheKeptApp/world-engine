# Community builds — execution brief

## Decision, MVP and boundaries

**R decided:** users create places in Builder and submit them for our approval before they appear on the shared map. Implement this as a reviewed, versioned public overlay over the OSM-derived base, not direct base-map editing or automatic publication. One general workflow for all places; no block-specific code. This brief specifies future work only: no service, moderation system, implementation or legal clearance is claimed.

**Recommended A12 MVP:** ship level 1 corrections and a small level 2 approved-module palette for private projects, using the same project/version model. Open public submission first for level 1 facts about existing mapped public-place footprints; add level 2 public placements only after review, aggregate budgets and rollback work end to end. This is a staged recommendation under R's new decision, not a promise of full community publishing in the first five-user pilot. Custom models are deferred. Private event layouts and AI proposals never become permanent map facts merely because someone submits them.

Inputs: [A12 Builder MVP](../research/builder-mvp-v1.md), [archetype registry](archetypes.md), [data-licensing](../data-licensing.md), [architecture contribution/access proposals](../architecture.md), [owner decisions](../decisions/owner-log.md), [Creator Kit UX approval](../proposals/creator-kit-ux-v3/STATUS.md), [event-template approval](../proposals/builder-event-templates-v1/STATUS.md), [venues approval](../proposals/venues-campuses-v1/STATUS.md). Existing architecture contribution policies remain proposals except where R's current decision establishes the submit/review/public-overlay direction. Builder remains after the engine look gate; A12's data-rights, ODbL-offer and independent shadow-validation gates remain. Events-first is a hypothesis, not a launch commitment.

## 1. Data model: snapshots, not mutable public projects

All schemas below are proposed. Product/service owns accounts, permissions and moderation; the engine consumes validated overlay data and has no account or review logic.

| Record | Required fields / invariant |
|---|---|
| `PrivateProject` | Opaque project ID, access policy/private by default, author account reference restricted to service, base package/version/hash, current draft revision. Private asset/evidence storage stays separate from published packages. A share link grants only its declared scope; no submission or publication rights. |
| `OverlayRevision` | Immutable revision ID + parent, schema version, base snapshot, stable source feature refs (OSM type+ID and/or GERS with source), registry/module versions, operations, coordinate reference/vertical datum, transforms in metres, source/provenance/licence references, declared observed/proposed/temporary status and optional validity dates. Content hash covers the exact revision. |
| `Operation` | `annotateFeature`, `proposeAttributeCorrection`, or `placeModule`; target ref and expected target geometry/property hash; changed fields only; dimensional provenance/uncertainty; module ID/version/allowed parameters. No raw tags that can execute rules, arbitrary URLs/scripts or silent feature deletions. |
| `Submission` | Immutable snapshot of selected revision/operations, submitter attestation version, purpose and factual basis, automation report version, status, private reviewer notes and public-safe decision reason. Submitting copies only selected operations and approved provenance, never the whole private project or its logo/media library. |
| `ReviewEvent` | Append-only event ID, actor role, timestamp, previous/new state, reason code, exact snapshot hash and check versions. Public history omits submitter identity, private comments and restricted evidence. |
| `PublicOverlayRevision` | New immutable publication ID referencing approved operations, approved base compatibility, module/registry/build hashes, public-safe attribution/provenance, effective dates, review expiry, predecessor, bounds and dependency set. Public state is an atomic pointer to a validated release, not a mutable draft. |
| `PublicationManifest` | Approved overlay set per region/version, aggregate budget result, signed/hash-verified content manifest and revoked IDs; base package unchanged. Clients resolve only eligible published records and honor revocations. |

### States and authority

`draft(private) → submitted → checking → ready_for_review → in_review → approved_pending_publish → published`.

Alternative transitions: checking → `needs_changes` for fixable issues or `quarantined` for unsafe/unreadable payloads; review → `needs_changes` / `rejected`; submitted/checking/review → `withdrawn` by author. Any draft edit after submission creates a new revision and requires a new submission/check; approval cannot follow a moving draft. Reviewer approval is required even when every automated check passes. Check failures cannot be overridden by changing a label: fix data or record an explicitly authorized exception and rerun relevant checks.

Published → `suspended` immediately for a credible privacy/rights/correctness issue; published → `superseded` on replacement; published → `expired` when validity/review expires. Reinstatement requires rechecks and human approval. Author withdrawal before publication is immediate; after publication it opens a removal request, with urgent privacy suspension available. Exact retention/removal obligations are for A11, not inferred from state names.

Only reviewer role may approve; only publication service may advance a checked, exact approved hash to published. The founder may initially hold both roles, with separate recorded actions and a final preview. Approval permissions never come from a project share link. Use optimistic version checks/idempotency keys so double clicks and concurrent reviews cannot publish twice. An “Approve” action does not publish a newer revision accidentally.

### Base map, registry and rollback

Resolve `base snapshot → approved factual overlay → private project overlay` for a private view; shared public views omit the private stage. Preserve provenance at every resolved field. A factual correction overlays a field for rendering/classification but does not mutate OSM or silently submit an OSM edit. A module replacement must explicitly reference the replaced representation and mask only that generated component, never erase the source footprint. The default for MVP placements is additive with overlap rejection; replacements need an explicit later reviewed operation.

[archetypes.md](archetypes.md) remains the common resolver. A reviewed correction may provide an explicit use/form fact; a user cannot bypass unknown fallback B with a suggestive name, per-block rule or arbitrary mesh. Re-run residential eligibility/conflicts with the current registry, and preserve Stage 0b's look-gate block and count/hold-out requirements. Submission approval does not authorize a global building-role change. Store original and resolved class with reasons. Temporary event props are an overlay, never a permanent building class.

On a base-map update, compare the target geometry/property hash, not just ID or nearest centroid. Changed/deleted/split targets put affected operations into `needs_rebase`, withholding them from the new public manifest until reviewed. Do not attach an old station correction to the nearest new building automatically. Unaffected overlays can move forward after compatibility checks. Concurrent same-field corrections are conflicts; no last-writer-wins. Compatible disjoint corrections can be composed only after combined validation.

Rollback publishes a new manifest pointing to the previous compatible revision and records why; never rewrites history. A revoked overlay is removed from future fetches and invalidates cached manifests. Clients need bounded cache lifetime, a revocation check and a public safe fallback to the base. Proposed maximum public manifest cache **24 hours**, shortened to immediate refresh when online after revocation; this is an implementation target, not a guarantee of deleting offline copies. No promise to recall screenshots or exported files. Dependents must be revalidated or suspended together. Author account deletion must not expose identity or silently destroy legally required audit records; A11 sets retention.

## 2. Three authoring levels

| Level | User actions | Constraints / MVP decision |
|---|---|---|
| 1 — correct an existing feature | Select an existing footprint, choose plain-language type/use, propose a measured attribute with source/date, preview before/after | **First public-submission slice.** No footprint creation/movement, demolition, owner/resident data or invented landmark. Restrict initial public pilot to non-sensitive public places; unknown evidence stays neutral. Geometry edits are a separate later capability. |
| 2 — approved modules | Place a versioned platform, shelter, stand or other approved module; choose bounded dimensions/material variants and terrain anchoring | **Private MVP palette; public promotion after level 1 works.** Each module must have runtime implementation, approval scope, LOD/cost metadata and provenance requirements. An approved concept sheet alone is not a shipping module. Tents/stages stay proposed/private or explicitly time-limited event overlays, never permanent map fixtures. |
| 3 — custom models | User supplies external geometry/materials | **Defer.** Needs sandboxed format parsing, decompression/resource caps, malware/content scan, licence/ownership proof, texture/metadata stripping, PII review, Style B conversion, dimensions/anchor verification, LOD/collision/shadow generation, combined performance validation, moderation previews and an appeal/removal process. No arbitrary shaders/scripts/external resource fetches. No upload path in MVP disguised as a module. |

Manual placement with an uploaded plan as private underlay comes first; AI proposes a layout second, with explicit user acceptance before it becomes a draft revision. AI is never an approver, factual authority or automatic publisher. Keep any underlay/evidence media private; public facts-only records carry structured provenance, not original uploaded plans. Evidence intake formats and retention need A11 review before implementation; this brief does not expand the existing media-upload policy.

## 3. Review workflow for one non-technical founder

One queue with **Ready**, **Needs information**, **Conflicts**, **Urgent removal**, and **History**. Keep technical logs behind “Details.” Show “What changes?”, a short source/date summary, exact map boundary, before/after toggle, street and aerial previews, and clear failures such as “Overlaps the sidewalk” or “Evidence needed.” Do not require the founder to inspect JSON, triangle counts or code to make a decision. Show a simple performance pass/fail with expandable measurements. Batch the view, not approvals: no blanket “approve all”.

Proposed operating limits, not measured capacity: invite-only pilot; at most **3 pending submissions per account**, **20 operations per submission**, one contiguous site. Rate-limit resubmissions and duplicate payloads; return structured feedback rather than endless retries. Queue capacity is a workload control, not a safety guarantee. No public SLA until review time is measured. Founder selects a ready item, checks provenance and appearance, chooses approve/request change/reject, previews exact publication, then confirms publish. An urgent “Hide from public map” control must work without editing geometry.

| Automated gate | What it can establish | Human decision still required |
|---|---|---|
| Permission/schema/version/hash | Authorized submitter, allowed fields/modules, exact snapshot, bounded payload, compatible base | Legitimate relationship to place; actual truth |
| Geometry validation | Finite coordinates, valid polygons, units, scale limits, terrain contact, no degenerate/inverted mesh; bounded geography | Plausible architecture and correct position from evidence |
| Overlap/clearance | Intersection with mapped buildings, water, roads, paths, module envelopes and other overlays | Whether mapped data is complete; actual access/clearance. Never claim permit, egress or structural safety from this gate |
| Performance | Offline composited scene budgets at frozen worst-case views, instance/material/pass counts, allowed LOD/material set | Whether quality is acceptable; counts alone do not prove phone frame rate |
| Content/privacy screening | Reject unapproved text/assets, personal-data patterns, embedded metadata, unsafe URLs; flag likely banned imagery if later allowed | False positives/negatives, subtle doxxing, rights, harassment, misleading claims. Automated “clean” is not approval |
| Provenance/conflict | Missing attestations, stale sources, duplicate target/field, changed base hashes, ambiguous associations | Which evidence is credible/current; whether to defer rather than choose |
| Look checks | Only approved module/palette IDs, no arbitrary emissive/shader/texture settings, scale and LOD bounds | Recognizable but restrained Style B; no misleading landmark imitation |

Banned-content checks in MVP are primarily **structural allowlists**, since users cannot publish arbitrary textures, text or models. Do not pretend an AI classifier guarantees moderation. Publish factual geometry/use only: no hateful or sexual graphics, threats, harassment, reputation labels, political/demographic coloring, executable payloads or misleading emergency/security instructions. Private reviewer evidence access is restricted and logged; don't put personal documents into public artefacts. Founder can ask for source clarification; inability to verify means needs information/reject, not guessed truth. Add report/takedown contact and appeal path before public pilot.

## 4. Style B, budgets and hold-outs

Keep real dimensions and mapped positions; approved matte materials, simplified surfaces and calibrated lighting belong to the engine. No per-submission light/exposure/haze override, photo façade, branded default, enlarged visibility prop or invented landmark. Module version pins its approved pack/sheet, renderer implementation, dimensions/allowed ranges, LODs, mesh/material cost and shadow behavior. Geometry facts override authored pack size. Palette constraints do not certify identity or ownership.

Evaluate **base + all currently active public overlays + proposed submission**, not each submission in isolation. Floor remains <400k main /≤150k shadow tris /≤100 main draws; standard prototype ≤500k/180k/120, per [budget brief](budget-tiers.md). Publication cannot silently raise floor or remove base houses/trees to make room. If the base already exceeds a required gate, record that debt and block a claimed pass. Two quality levels are a recommendation pending device qualification, not existing infrastructure. Public module support needs a legal fallback at both required levels; never hide a factual correction merely to make one benchmark pass. Memory, frame timing and approved shadow reach remain independent checks.

At intake, compute exact static module topology and an incremental estimate; before publication validate the **composited** release against representative near/far, boundary and overlapping-site views. Unknown shadow counts are pending, not zero. A proposed 20-operation limit is not a triangle allowance. Adjacent approved sites may be individually cheap and jointly over budget; manifest validation reserves shared per-view headroom and rejects incompatible combinations. LOD/instancing rules stay general.

Freeze baseline hold-outs Lakeview, Wilmette, West Highland and Greenville (when data/contracts ready), plus Sloan focus; keep no-submission controls. A new local factual overlay changes its own site intentionally, so capture that before/after and confirm unrelated hold-outs stay unchanged. A new module, registry policy or renderer change requires full A3 blind scoring across all applicable hold-outs, not only the contributor's site. No aspect/overall decline; absent data stays pending. Test composite stress fixtures separately from real hold-outs. Founder reviews every publish preview; A3 qualifies reusable module/pipeline changes rather than becoming an indefinite per-submission bottleneck. If a submission needs a new visual mechanism, return it to that qualification queue.

## 5. Landmark, privacy, rights and conflict rules

The shared map represents places, not residents or private lives. No resident/owner names, home association, personal routines, track histories, identifiable faces, private interiors, sensitive-site internal layouts or demographic/reputation overlays. Public provenance uses dataset/source credits, not contributor identity, home location or activity feed. Public-place pilot scope excludes private-home personalization: existing on-device home customization must never be silently submitted or uploaded. Later residential exterior corrections need explicit policy and resident opt-out handling, reviewed by A11. Submission coordinates are inherently location data; access controls and minimized logs still matter even without a name.

Private uploaded logos/brand assets are allowed under R's decision, but **private permission is not public-map permission**. Engine ships no brands. Strip private logo/plan assets from public submission payloads; a future licensed public-brand exception requires specific rights and owner approval, not a checkbox asserting ownership alone. No public art/sculpture replication or landmark-specific model without clearance and the separate approved landmark process. A generic stadium module is not authority to copy a famous stadium or use school/team/sponsor marks. A landmark name or OSM tag cannot bypass that process.

Conflicting OSM and contributor facts: keep base immutable, compare dated evidence and scope; reviewer may approve a clearly provenance-labelled overlay while retaining the original, request correction or reject. No automatic outbound OSM edit. Conflicting users: merge disjoint compatible fields only after checks; competing same-field edits remain queued with no priority from payment/popularity or latest timestamp alone. If uncertainty is material, use neutral registry fallback. Ownership claims do not grant factual authority or exclusivity over a public place. Appeals are reviewed on evidence, with a reason and rollback trail.

A11 must settle before public release: contributor licence sufficient for hosting/modification/rendering/distribution and sublicensing where needed; attribution; private-to-public consent; uploaded evidence rights; personal-data retention/deletion and takedowns; public-art/architecture/trademark rules by jurisdiction; ODbL classification of public corrections and the required database offer. [Current data policy](../data-licensing.md) treats private overrides separately; **do not assume that exemption covers a shared approved overlay**. Keep public factual layer, proprietary module assets and private project data separable in storage/manifests, but separation alone is not a legal conclusion. Existing ODbL offer/release gate still applies, including A11's unresolved invite-only-pilot question. R's product decision does not resolve these rights questions.

Proposed permanent factual overlays require revalidation on base change and a **180-day review date**; temporary/event overlays require explicit start/end and expire at end, never auto-repeat. These periods are operational starting proposals for R, not prior policy. Expiry removes an unverified contribution from the active manifest without destroying audit evidence under the eventual retention policy. A fully verified evergreen correction may have a longer reviewed interval, recorded explicitly; never quietly become base-map truth.

## 6. Build order, reuse and acceptance

| Stage / proposed owner | Smallest useful delivery | Acceptance tests |
|---|---|---|
| 0 — A12 product + A11 rights; A3 gate filing | Define allowlisted corrections/modules, consent/rights language, queue preview and release gates | No claim of public readiness with unresolved offer/rights; private-home personalization cannot enter submit flow; only approved runtime modules selectable |
| 1 — Builder/service owner (assignment required) | Private versioned projects and level1/limited level2 manual authoring; immutable submission snapshots | Edit after submit creates new revision; share link cannot approve; unselected private assets absent; invalid geometry/unknown module rejected; AI suggestion remains unaccepted draft |
| 2 — service owner + founder | Automated checks, reviewer queue, request-change/reject/approve actions; no public rollout yet | Permission bypass fails; duplicate submit idempotent; approving stale hash fails; failed gate cannot publish; mixed-use/unknown registry fallbacks preserved |
| 3 — service + map/package owners, A3 | Atomic public overlay manifest, revocation/rollback; small level1 public-place pilot once gates pass | Exact approved revision visible; base hash unchanged; rollback restores prior compatible state; client rejects altered manifest; expired/revoked overlay absent after bounded refresh; offline limitation documented |
| 4 — P2 modules / 5A native / A2 web, with service owner | Public level2 approved placements, aggregate budgets, LOD and compositing | Two individually valid overlapping submissions fail combined check; standard and floor gaps explicit; no changed shadow reach; package/native/web identity match; A3 no hold-out decline |
| 5 — later decision | Broader annotation/landmark workflows, eventual custom models | Separate rights/content/ingestion/LOD qualification; no custom file upload before all deferred prerequisites exist |

Additional synthetic cases: changed OSM footprint invalidates binding; deleted/split feature never snaps to neighbor; same-field concurrent approvals cannot race; disjoint edits recompute combined costs; unknown footprint plus “Station House” name stays neutral; verified use correction follows registry without per-place code; proposed wedding tents expire and never classify as permanent buildings; privacy report suspends public revision without exposing complainant; malicious name/source URL never becomes executable markup; repeat submissions cannot exhaust render workers. Author attestation alone cannot pass a rights conflict. Render workers need resource limits and isolated inputs even when only approved modules are allowed.

Reusable now versus merely specified:

- `docs/proposals/creator-kit-ux-v3/app.js` and version/export/share designs: reusable interaction/schema ideas and local prototype behavior; **not production accounts, authorization, backend persistence or protected sharing**. Shared view is not the public-map publication service.
- `docs/proposals/builder-event-templates-v1/parametric-parts.json`, `common-rules.json`, `rules/` and venues sheets: reusable proposed dimensions/categories/envelopes after runtime/approval verification; not certified collision, capacity, permit or evacuation checks.
- [A12](../research/builder-mvp-v1.md): shared outdoor planner, dimensioned objects, date/time and reproducible version/export concept; no completed customer conversations or implementation inferred. Reuse its independent shadow-validation and data-provenance requirements.
- Existing map feature IDs, generator/module work, package/credit manifests and [archetypes](archetypes.md): foundations for deterministic refs, look and licence provenance; no claim a community overlay loader already exists. A4 is package/export handoff, A1 map-data provenance; exact production service owner must be assigned before implementation.
- `event-sitemap-ai-v1` is research/prototype only. Manual underlay/placement first, AI second. Neither the image-based UX nor its sliders proves live 3D updates or recalculated shadows.

No new code paths, hosting, accounts, uploads or outward messages are created here. Builders must update implementation/consumption evidence when shipping; this document changes only the execution proposal.
